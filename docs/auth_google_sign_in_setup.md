# AUTH-5 — Google Sign-In setup

## Implemented strategy

Rutio uses native Google Sign-In on Android and iOS. The app obtains a Google
ID token with `google_sign_in` 7.2.0 and exchanges it immediately with
`supabase_flutter` 2.12.4 / GoTrue 2.20.0 through:

```dart
supabase.auth.signInWithIdToken(
  provider: OAuthProvider.google,
  idToken: idToken,
  accessToken: accessToken,
)
```

The access token is requested from the SDK authorization client for the
`openid`, `email`, and `profile` scopes. Tokens are never logged or persisted
by Rutio. `serverAuthCode` is not requested. Native sign-in is kept behind
`GoogleAuthAdapter`; the resulting Supabase session enters the existing
AuthController/Bootstrap or onboarding state machine.

## Google Cloud steps

1. Select the Google Cloud project owned by Rutio, or create one under the
   organization's account.
2. In Google Auth Platform → Branding, set app name `Rutio`, support email,
   developer contact email, and the authorized domain `rutioapp.com` if the
   console requests a web domain.
3. If the consent screen is in Testing, add the QA Google accounts as test
   users. Move to Production after verification/approval requirements are met.
4. Create an OAuth Client ID of type **Android** with package
   `com.rutio.app`. Add the debug and upload SHA-1 fingerprints when the
   console asks for certificate fingerprints; also add the Play App Signing
   certificate before Play-distributed QA. The known SHA-1 values are in
   `docs/auth_deep_link_domain_setup.md`.
5. Create an OAuth Client ID of type **iOS** for bundle `com.rutio.app`.
   Copy its public Client ID and register the reversed client ID as the iOS
   URL scheme required by `google_sign_in_ios`. This requires a real value and
   is intentionally not added as a placeholder here.
6. Create an OAuth Client ID of type **Web application**. Save its public
   Client ID; it is the `GOOGLE_WEB_CLIENT_ID` / Android `serverClientId` used
   for the native Supabase ID-token exchange. No web callback is needed for
   this native flow.

## Supabase Dashboard steps

1. Open Authentication → Providers → Google.
2. Enable Google.
3. Set **Client ID** to the web Client ID first, followed by the iOS and
   Android Client IDs if the Dashboard field supports multiple IDs (comma
   separated, web first, as documented by Supabase).
4. Set **Client Secret** to the web OAuth Client Secret in the Dashboard only.
   It must never enter the Flutter app.
5. Leave nonce checking at the provider default; AUTH-5 does not invent an
   Apple nonce flow or enable `skip_nonce_check`.
6. Keep the existing canonical redirect URL
   `https://www.rutioapp.com/auth/callback` and Confirm Email **OFF**. Native
   Google sign-in does not change the password-recovery callback contract.

## Platform integration

Android uses the direct Google Cloud registration and does not add Firebase,
`google-services.json`, or the Gradle Google Services plugin. Build/test with:

```powershell
flutter run --dart-define=SUPABASE_URL=... --dart-define=SUPABASE_ANON_KEY=... `
  --dart-define=GOOGLE_WEB_CLIENT_ID=...
```

iOS is statically prepared by the Dart `clientId`/`serverClientId` path. Add
the real iOS reversed-client-ID URL scheme to `ios/Runner/Info.plist` (or the
official equivalent generated by the native setup) after Google Cloud creates
the client. Preserve `applinks:www.rutioapp.com` in the existing entitlements.

## Product and security contract

- Login and final onboarding both show only “Continue with Google”; Apple is
  not shown.
- Cancellation returns to the same screen and preserves the onboarding draft.
- Network/provider/configuration/credential/conflict failures are typed and
  shown as safe copy; raw provider exceptions are not shown.
- Existing account resolution remains remote-authoritative. New Google users
  use the existing profile-shell and onboarding completion path; no password,
  confirmation gate, second draft, or second completion path is created.
- Same-email email/password and Google identities are not manually linked by
  AUTH-5. Any Supabase identity conflict fails closed and is reported as a
  retryable Google sign-in error.
- Logout signs out Supabase and best-effort signs out the Google SDK so the
  next login can choose another account. Account deletion remains the existing
  remote deletion flow.
